## 2. Теоретический конспект

### 2.1. Автоматизированное UI-тестирование

Автоматизация UI-тестирования позволяет сократить объём повторяемой ручной работы и делает проверку пригодной для регулярного запуска после изменений приложения . Ключевая проблема UI-тестов — асинхронность браузерного интерфейса: элемент может присутствовать в DOM, но оставаться невидимым или недоступным для взаимодействия .

### 2.2. Selenium WebDriver

Selenium WebDriver предоставляет единый интерфейс управления браузером . Для синхронизации используются явные ожидания (WebDriverWait), которые приостанавливают выполнение до наступления конкретного состояния элемента .

```java
// Явное ожидание появления элемента
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("username")));
```

### 2.3. Page Object Model (POM)

Паттерн Page Object Model предполагает, что каждая страница представляется отдельным классом, содержащим элементы и методы взаимодействия с ними . Это улучшает читаемость и переиспользуемость кода.

**Пример класса LoginPage:**

```java
public class LoginPage {
    private WebDriver driver;
    
    @FindBy(id = "username")
    private WebElement usernameField;
    
    @FindBy(id = "password")
    private WebElement passwordField;
    
    @FindBy(id = "login-btn")
    private WebElement loginButton;
    
    public LoginPage(WebDriver driver) {
        this.driver = driver;
        PageFactory.initElements(driver, this);
    }
    
    public HomePage login(String username, String password) {
        usernameField.sendKeys(username);
        passwordField.sendKeys(password);
        loginButton.click();
        return new HomePage(driver);
    }
    
    public String getErrorMessage() {
        return driver.findElement(By.id("error-msg")).getText();
    }
}
```

### 2.4. Сценарный подход к тестированию

Тестовый случай представляется как кортеж **T = (P, D, A, W, E)**, где:
- **P** — предусловия
- **D** — тестовые данные
- **A** — последовательность действий
- **W** — условия ожидания
- **E** — ожидаемое наблюдаемое состояние 

**Матрица сценариев для формы входа:**

| Сценарий | Логин | Пароль | Ожидаемый результат |
|----------|-------|--------|---------------------|
| Позитивный | valid@mail.ru | ValidPass123 | Переход на главную страницу |
| Негативный | valid@mail.ru | wrong | Сообщение об ошибке |
| Негативный | wrong@mail.ru | ValidPass123 | Сообщение об ошибке |
| Негативный | (пусто) | (пусто) | Сообщение об ошибке |

## 2. Теоретический конспект

### 2.1. Модульное тестирование

Модульное тестирование проверяет отдельные компоненты программы в изоляции от других компонентов . JUnit 5 — основной фреймворк для модульного тестирования в Java.

### 2.2. Основные аннотации JUnit 5

| Аннотация | Описание |
|-----------|----------|
| `@Test` | Помечает метод как тест |
| `@BeforeEach` | Выполняется перед каждым тестом |
| `@AfterEach` | Выполняется после каждого теста |
| `@BeforeAll` | Выполняется один раз перед всеми тестами |
| `@DisplayName` | Задаёт отображаемое имя теста |
| `@ParameterizedTest` | Параметризованный тест |

### 2.3. Mockito

Mockito позволяет создавать mock-объекты для изоляции тестируемого кода .

```java
// Создание мока
UserRepository repository = mock(UserRepository.class);

// Настройка поведения
when(repository.findById(1L)).thenReturn(Optional.of(user));
when(repository.save(any(User.class))).thenReturn(savedUser);

// Проверка вызовов
verify(repository).findById(1L);
verify(repository, times(1)).save(any(User.class));
```

### 2.4. Утверждения

```java
import static org.junit.jupiter.api.Assertions.*;

// Проверка значений
assertEquals(expected, actual);
assertTrue(condition);
assertThrows(Exception.class, () -> method());

// Групповые проверки
assertAll("user validation",
    () -> assertEquals("John", user.getFirstName()),
    () -> assertEquals("Doe", user.getLastName())
);
```

## 2. Теоретический конспект

### 2.1. ИИ-инструменты для генерации тестов

Современные ИИ-инструменты способны анализировать исходный код и генерировать тесты с осмысленными утверждениями (assertions), учитывая контекст, зависимости и краевые случаи .

**Популярные решения:**
- **JAIPilot** — AI-плагин для IntelliJ IDEA, генерирует тесты по правому клику на классе .
- **GitHub Copilot** — поддерживает генерацию тестов через чат-интерфейс .
- **TestSpark** — исследовательский плагин от JetBrains .

### 2.2. Принципы работы ИИ-агентов

Процесс генерации тестов обычно состоит из трёх этапов :

1. **Сбор контекста:** анализ метода, его параметров, зависимостей и краевых случаев .
2. **Генерация:** создание тестов с осмысленными проверками.
3. **Обратная связь:** попытка запуска и автоматическое исправление ошибок .

### 2.3. Ограничения ИИ-генерации тестов

При использовании ИИ важно учитывать ограничения :

- ИИ может генерировать код, выглядящий технически корректно, но не выполняющий ожидаемые проверки.
- Отсутствие контекста (неизвестный URL, маршрутизация, бизнес-правила) .
- Риск галлюцинаций — несуществующие методы или библиотеки.
- **Обязательная проверка** сгенерированного кода перед использованием .

### 2.4. Эффективные промпты для генерации тестов

**Пример промпта для GitHub Copilot :**
```
Generate unit tests for this Java project using #appmod-generate-tests-for-java
```

**Структура промпта:**
- **Цель (Goal):** что нужно сделать
- **Контекст (Context):** о каком проекте идёт речь
- **Правила (Rules/Style):** какие соглашения соблюдать
- **Формат вывода (Output Format):** ожидаемая структура ответа
