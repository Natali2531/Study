## 2. Теоретический конспект

### 2.1. Тестирование формы входа

**Основные требования к форме входа:**

1. **Доступность:** форма должна быть легко найдена на сайте (на виду или доступна в один клик).

2. **Элементы формы:** должна содержать поля для логина и пароля, кнопку входа и ссылку «забыли пароль?».

3. **Курсор:** после загрузки формы курсор должен находиться в поле ввода логина.

4. **Регистрация:** форма должна содержать ссылку на регистрацию.

5. **Валидация:** 
   - Нельзя авторизоваться с неверными логином и паролем.
   - Должно быть предупреждение о незаполненном поле.
   - Сообщения об ошибках должны быть понятными.

6. **Ограничения:** 
   - Ограничение на количество символов.
   - Ограничение на число неудачных попыток (защита от подбора пароля).

7. **Безопасность:**
   - Чувствительность к регистру для пароля.
   - Маскировка символов пароля.
   - Минимальная длина пароля.

8. **UX:** 
   - Пользователь должен понимать, авторизирован он или нет.
   - Кнопки браузера «вперед» и «назад» не должны нарушать состояние авторизации.

### 2.2. Чек-лист для тестирования формы входа мобильного приложения

| Раздел | Проверки |
|--------|----------|
| **Функциональное тестирование** | Успешный вход с валидными данными, блокировка при неверных данных, проверка полей ввода, переключение видимости пароля, очистка полей, вход по отпечатку пальца/Face ID, вход через соцсети |
| **UI-тестирование** | Верстка, выравнивание, шрифты, адаптация под светлую/темную тему, интерактивность, масштабирование текста, локализация |
| **UX-тестирование** | Навигация (клавиатура, кнопки), ссылки и переходы, обратная связь, запоминание данных |
| **Безопасность** | HTTPS, пароль скрыт, защита от скриншотов, брутфорс-защита, безопасное хранение, отсутствие утечки данных в логах |
| **Производительность** | Скорость отклика, поведение при потере связи, работа с медленным соединением |
| **Интеграционное тестирование** | Работа с клавиатурами сторонних производителей, менеджеры паролей, переход после входа, выход из аккаунта |
| **Кросс-платформенное** | Смена ориентации, прерывания (звонок, SMS, уведомления), работа на разных версиях ОС |

### 1.2. Задачи работы

---

## 2. Теоретический конспект

### 2.1. Структура баг-репорта

**Баг-репорт** — технический документ, описывающий дефект в программном обеспечении.

**Обязательные поля:**
- **Короткое описание (Bug Summary)** — краткое описание проблемы.
- **Серьезность (Severity)** — степень влияния дефекта на работу системы.
- **Шаги к воспроизведению (Steps to Reproduce)** — последовательность действий для воспроизведения.
- **Результат (Actual Result)** — что происходит на самом деле.
- **Ожидаемый результат (Expected Result)** — что должно происходить.

**Дополнительные поля:**
- Приоритет (Priority)
- Статус (Status)
- Окружение (Environment)
- Вложения (Attachments)

### 2.2. Градация серьезности дефекта (Severity)

| Уровень | Обозначение | Описание |
|---------|-------------|----------|
| **S1** | **Blocker** | Блокирующая ошибка, приводящая приложение в нерабочее состояние. Дальнейшая работа невозможна. |
| **S2** | **Critical** | Критическая ошибка, неправильно работающая ключевая бизнес-логика, дыра в безопасности. |
| **S3** | **Major** | Значительная ошибка, часть основной бизнес-логики работает некорректно, но есть обходной путь. |
| **S4** | **Minor** | Незначительная ошибка, не нарушающая бизнес-логику, проблема пользовательского интерфейса. |
| **S5** | **Trivial** | Тривиальная ошибка, не касающаяся бизнес-логики, плохо воспроизводимая проблема. |

### 2.3. Градация приоритета дефекта (Priority)

| Уровень | Обозначение | Описание |
|---------|-------------|----------|
| **P1** | **High** | Ошибка должна быть исправлена как можно быстрее, т.к. ее наличие критично для проекта. |
| **P2** | **Medium** | Ошибка должна быть исправлена, ее наличие не критично, но требует обязательного решения. |
| **P3** | **Low** | Ошибка должна быть исправлена, ее наличие не критично и не требует срочного решения. |

**Порядок исправления:** High → Medium → Low

### 2.4. Принцип «Где? Что? Когда?»

При написании короткого описания следуйте принципу:

1. **Где?** — В каком месте интерфейса находится проблема.
2. **Что?** — Что происходит или не происходит.
3. **Когда?** — При каких условиях проблема проявляется.

**Примеры:**
- ❌ Плохо: "Не работает кнопка"
- ✅ Хорошо: "Кнопка 'Сохранить' на форме 'Профайл' неактивна при заполнении всех обязательных полей"

### 2.5. Основные ошибки при написании баг-репортов

1. **Недостаточность предоставленных данных** — не указаны входные данные, пользователь, окружение.
2. **Неверное определение серьезности** — завышение или занижение.
3. **Неправильный язык описания** — использование нетехнической терминологии.
4. **Отсутствие ожидаемого результата** — не указано, что должно быть.

## 2. Теоретический конспект

### 2.1. Чек-лист

**Чек-лист** — список проверок, помогающий тестировщику протестировать приложение и не забыть проверить всё запланированное.

**Структура чек-листа:**
- 1-й столбец: заголовки тест-кейсов или пункты проверок
- 2-й столбец: отметка pass/fail
- 3-й столбец: заметки (опционально)

### 2.2. Классы эквивалентности

**Класс эквивалентности** — множество значений, которые обрабатываются системой одинаково.

**Типы классов:**
1. **Непрерывные классы** — диапазон значений (например, доход от $1000 до $83333)
2. **Дискретные классы** — отдельные значения (например, 1-5 домов)
3. **Классы с одним возможным значением** (например, "человек")
4. **Классы с несколькими возможными значениями** (например, типы жилья)

**Правило:** для каждого класса эквивалентности достаточно одного теста.

### 2.3. Граничные значения

**Граничные значения** — значения на границах классов эквивалентности.

**Почему важно тестировать границы:**
- Ошибки чаще всего возникают именно на границах допустимых значений.
- Разработчики часто допускают ошибки в условиях (<= вместо <).

**Пример:**
- Допустимый диапазон: 0.01 - 50 кг
- Граничные значения: 0.01, 0.02, 49.99, 50.00, 50.01, 0.00, -1

## 2. Теоретический конспект

### 2.1. Комбинаторное тестирование с ограничениями

При тестировании конфигураций часто существуют бизнес-ограничения, которые исключают некоторые комбинации.

**Пример ограничений:**
- С Intel i5 нельзя выбрать 32 ГБ ОЗУ
- С интегрированной видеокартой нельзя выбрать NVIDIA RTX 3060
- HDD доступен только с Intel i5 или AMD Ryzen 7

**Алгоритм:**
1. Рассчитать количество комбинаций при полном переборе.
2. Исключить невалидные комбинации согласно ограничениям.
3. Применить попарное тестирование к оставшимся комбинациям.

### 2.2. Диаграмма состояний и переходов

**Диаграмма состояний** — модель поведения системы, показывающая состояния и переходы между ними.

**Состояния (States):**
- Off (Выключена)
- Ready (Готова)
- Brewing (Приготовление)
- Error (Ошибка)

**Переходы (Transitions):**
- Off → Ready: POWER (при наличии воды и зерен)
- Ready → Brewing: START
- Brewing → Ready: Таймаут 2 минуты
- Ready → Error: Нет воды или нет зерен
- Error → Ready: Долита вода и добавлены зерна
- Любое → Off: Долгое нажатие POWER

### 2.3. Таблица переходов

| Из состояния | Событие | Условие | В состояние |
|--------------|---------|---------|-------------|
| Off | POWER | есть вода и зерна | Ready |
| Off | POWER | нет воды или зерен | Error |
| Ready | START | — | Brewing |
| Ready | Таймаут | 2 минуты | Ready |
| Ready | Ошибка | нет воды или зерен | Error |
| Error | POWER | есть вода и зерна | Ready |
| Любое | POWER | долгое нажатие 3 сек | Off |

### 2.4. Критичные тестовые сценарии

1. **Основной счастливый путь:** Off → Ready → Brewing → Ready → Off
2. **Восстановление из ошибки:** Ready → Error → Ready
3. **Аварийное выключение:** Brewing → Off (долгое нажатие)
4. **Двойная ошибка:** Error → Error (повторная попытка без исправления)
5. **Крайнее условие:** Закончились зерна точно в момент нажатия START

### 2.5. «Зловредные» (mischievous) тесты

Тесты, проверяющие неочевидное поведение:
- Нажать START, когда кофе уже готовится
- Открыть отсек для воды во время приготовления
- Долгое нажатие POWER во время ошибки
- Быстрое переключение POWER → START → POWER

## 2. Теоретический конспект

### 2.1. Автоматизированное UI-тестирование

Автоматизация UI-тестирования позволяет сократить объём повторяемой ручной работы и делает проверку пригодной для регулярного запуска после изменений приложения . Ключевая проблема UI-тестов — асинхронность браузерного интерфейса: элемент может присутствовать в DOM, но оставаться невидимым или недоступным для взаимодействия .

### 2.2. Selenium WebDriver

Selenium WebDriver предоставляет единый интерфейс управления браузером . Для синхронизации используются явные ожидания (WebDriverWait), которые приостанавливают выполнение до наступления конкретного состояния элемента .

```java
// Явное ожидание появления элемента
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("username")));
```

### 2.3. Page Object Model (POM)

Паттерн Page Object Model предполагает, что каждая страница представляется отдельным классом, содержащим элементы и методы взаимодействия с ними . Это улучшает читаемость и переиспользуемость кода.

**Пример класса LoginPage:**

```java
public class LoginPage {
    private WebDriver driver;
    
    @FindBy(id = "username")
    private WebElement usernameField;
    
    @FindBy(id = "password")
    private WebElement passwordField;
    
    @FindBy(id = "login-btn")
    private WebElement loginButton;
    
    public LoginPage(WebDriver driver) {
        this.driver = driver;
        PageFactory.initElements(driver, this);
    }
    
    public HomePage login(String username, String password) {
        usernameField.sendKeys(username);
        passwordField.sendKeys(password);
        loginButton.click();
        return new HomePage(driver);
    }
    
    public String getErrorMessage() {
        return driver.findElement(By.id("error-msg")).getText();
    }
}
```

### 2.4. Сценарный подход к тестированию

Тестовый случай представляется как кортеж **T = (P, D, A, W, E)**, где:
- **P** — предусловия
- **D** — тестовые данные
- **A** — последовательность действий
- **W** — условия ожидания
- **E** — ожидаемое наблюдаемое состояние 

**Матрица сценариев для формы входа:**

| Сценарий | Логин | Пароль | Ожидаемый результат |
|----------|-------|--------|---------------------|
| Позитивный | valid@mail.ru | ValidPass123 | Переход на главную страницу |
| Негативный | valid@mail.ru | wrong | Сообщение об ошибке |
| Негативный | wrong@mail.ru | ValidPass123 | Сообщение об ошибке |
| Негативный | (пусто) | (пусто) | Сообщение об ошибке |

// Создание мока
UserRepository repository = mock(UserRepository.class);

verify(repository).findById(1L);

import static org.junit.jupiter.api.Assertions.*;

assertAll("user validation",

);

## 2. Теоретический конспект

### 2.1. ИИ-инструменты для генерации тестов

Современные ИИ-инструменты способны анализировать исходный код и генерировать тесты с осмысленными утверждениями (assertions), учитывая контекст, зависимости и краевые случаи .

**Популярные решения:**
- **JAIPilot** — AI-плагин для IntelliJ IDEA, генерирует тесты по правому клику на классе .
- **GitHub Copilot** — поддерживает генерацию тестов через чат-интерфейс .
- **TestSpark** — исследовательский плагин от JetBrains .

### 2.2. Принципы работы ИИ-агентов

Процесс генерации тестов обычно состоит из трёх этапов :

1. **Сбор контекста:** анализ метода, его параметров, зависимостей и краевых случаев .
2. **Генерация:** создание тестов с осмысленными проверками.
3. **Обратная связь:** попытка запуска и автоматическое исправление ошибок .

### 2.3. Ограничения ИИ-генерации тестов

При использовании ИИ важно учитывать ограничения :

- ИИ может генерировать код, выглядящий технически корректно, но не выполняющий ожидаемые проверки.
- Отсутствие контекста (неизвестный URL, маршрутизация, бизнес-правила) .
- Риск галлюцинаций — несуществующие методы или библиотеки.
- **Обязательная проверка** сгенерированного кода перед использованием .

### 2.4. Эффективные промпты для генерации тестов

**Пример промпта для GitHub Copilot :**
```

```

**Структура промпта:**
- **Цель (Goal):** что нужно сделать
- **Контекст (Context):** о каком проекте идёт речь
- **Правила (Rules/Style):** какие соглашения соблюдать
