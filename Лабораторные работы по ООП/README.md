<content># Введение

Настоящие методические указания разработаны в соответствии с рабочей программой дисциплины «Объектно-ориентированное программирование» и предназначены для организации лабораторных занятий со студентами 2 курса направления подготовки 09.03.04 «Программная инженерия».

## Место дисциплины в образовательной программе

Дисциплина «Объектно-ориентированное программирование» является базовой дисциплиной вариативной части учебного плана и изучается в 3 семестре. Она опирается на знания, полученные студентами в ходе изучения дисциплин «Алгоритмы и структуры данных», «Основы программирования» и «Информатика». Материал дисциплины служит основой для последующего изучения «Технологий разработки программного обеспечения», «Баз данных», «Веб-программирования» и других профильных дисциплин.

## Особенности дисциплины

Отличительной особенностью настоящей дисциплины является **сквозное применение средств искусственного интеллекта** на всех этапах обучения — от генерации шаблонов классов до рефакторинга, написания тестов и проектирования архитектуры. При этом средства ИИ рассматриваются не как замена разработчику, а как инструмент, требующий критического осмысления и проверки.

Важным ограничением является то, что все применяемые ИИ-инструменты должны быть **доступны на территории Российской Федерации без использования средств обхода блокировок (VPN)**. Это требование обусловлено необходимостью обеспечения стабильного доступа к инструментам для всех обучающихся и соблюдения законодательства Российской Федерации.

## Цели лабораторного практикума

Лабораторный практикум преследует следующие цели:

1. **Формирование практических навыков** объектно-ориентированного проектирования и программирования на языке Java.
2. **Освоение современных инструментов** разработки: интегрированных сред, систем сборки, систем контроля версий.
3. **Развитие навыков работы со средствами ИИ** как инструментами ускорения разработки при сохранении критического мышления.
4. **Формирование умения** работать с файловой системой, базами данных, многопоточностью и внешними API.
5. **Освоение методологии ETL** (Extract, Transform, Load) как основы для работы с данными в серверной разработке.
6. **Развитие навыков командной работы** при выполнении итогового мини-проекта.

## Сквозная предметная область

Для обеспечения преемственности материала и возможности постепенного усложнения задач в рамках лабораторного практикума используется **сквозная предметная область** — работа с данными о книгах. На разных этапах обучающиеся:

- создают класс `Book` и работают с его объектами (лаб. 1–3);
- организуют хранение книг в коллекциях (лаб. 4);
- создают универсальные хранилища `Repository<T>` (лаб. 5);
- обрабатывают исключения при работе с книгами (лаб. 6);
- читают данные о книгах из CSV, JSON и XML (лаб. 7–8);

В итоговом мини-проекте (лаб. 16–17) предметная область может быть изменена по согласованию с преподавателем.

## 4. Требования к программному коду

Код, представляемый на защиту, должен соответствовать следующим требованиям:

1. **Соглашения об именовании** (Java Code Conventions):
   - классы — `CamelCase` (например, `BookRepository`);
   - методы и переменные — `camelCase` (например, `findByTitle`);
   - константы — `UPPER_SNAKE_CASE` (например, `MAX_BOOKS_PER_USER`);
   - пакеты — строчными буквами (например, `com.university.lab01`).

2. **Стиль кода**:
   - отсутствие «магических чисел» — использование именованных констант;
   - осмысленные имена переменных и методов;
   - отсутствие дублирующегося кода;
   - разумная длина методов (рекомендуется не более 30 строк).

3. **Документирование**:
   - Javadoc-комментарии к публичным классам и методам;
   - пояснительные комментарии к сложным участкам кода.

4. **Обработка ошибок**:
   - отсутствие «проглоченных» исключений (пустых блоков `catch`);
   - использование специализированных типов исключений;
   - закрытие ресурсов в `try-with-resources`.

5. **Типобезопасность**:
   - отсутствие «сырых» типов (raw types) при работе с обобщениями;
   - минимизация приведений типов.

# Политика применения средств искусственного интеллекта

## 1. Общие принципы

Применение средств искусственного интеллекта в рамках дисциплины является **обязательным элементом обучения**, а не опциональным. Обучающиеся должны не только уметь применять ИИ-инструменты, но и критически оценивать результаты их работы, понимать ограничения и области эффективного применения.

**Ключевой принцип:** ИИ-ассистент — это стажёр-программист, а обучающийся — тимлид. Задача обучающегося — ставить чёткие задачи, проверять результат, находить ошибки и доводить решение до требуемого качества.

## 2. Допустимые ИИ-инструменты

В рамках дисциплины разрешается применение **только тех ИИ-инструментов, которые доступны на территории Российской Федерации без использования VPN**. К допустимым инструментам относятся:

| Инструмент | Провайдер | Доступ |
|------------|-----------|--------|
| **YandexGPT** | Яндекс (yandex.cloud/ru/services/yandexgpt) | Бесплатный тариф, API |
| **GigaChat** | Сбер (giga.chat) | Бесплатный тариф, API |
| **Qwen** | Различные российские провайдеры | Через Yandex Cloud, Timeweb Cloud |
| **Ollama** | Локальный запуск (ollama.com) | Полностью локально |
| **JetBrains AI Assistant** | Встроен в IntelliJ IDEA | Доступен в РФ |
| **CodeGeeX** | Локальный плагин для IDE | Бесплатно |

**Запрещено использование** (недоступно в РФ без VPN):

- Google Gemini.

Подробный список инструментов с инструкциями по настройке приведён в **Приложении А**.

## 3. Допустимые сценарии применения ИИ

**Разрешается:**
- генерация шаблонного кода (boilerplate): getter'ы, setter'ы, конструкторы;
- генерация классов-исключений по описанию;
- генерация модульных тестов по сигнатуре метода;
- рефакторинг кода с улучшением читаемости;
- объяснение незнакомых языковых конструкций и сообщений компилятора;
- генерация SQL-запросов по текстовому описанию;
- генерация регулярных выражений;
- помощь в проектировании архитектуры (с последующей критической оценкой);
- написание Javadoc-комментариев.

**Не допускается:**
- полное делегирование проектирования архитектуры без понимания;
- копирование сгенерированного кода без проверки и понимания;
- использование ИИ для написания отчёта вместо обучающегося;
- передача в ИИ конфиденциальных данных, персональных данных третьих лиц, API-ключей.

## 4. Документирование применения ИИ

Обучающийся обязан вести **журнал применения ИИ** в директории `docs/prompts/` проекта. Для каждого случая применения ИИ фиксируется:

1. **Дата и инструмент** — какой ИИ-инструмент применялся.
2. **Промпт** — точный текст запроса к ИИ.
3. **Результат ИИ** — сгенерированный код или ответ (можно в сокращённом виде).
4. **Анализ результата** — что верно, что требует доработки, какие ошибки обнаружены.
5. **Внесённые изменения** — что было исправлено и почему.

**Пример записи в журнале:**

```markdown
### 2026-09-15 | YandexGPT | Генерация класса BookNotFoundException

**Промпт:**
«Создай checked-исключение BookNotFoundException на Java 17.
Класс должен содержать конструкторы с сообщением и с сообщением + причиной.
Добавь поле bookId типа long и соответствующий геттер.»

**Результат ИИ:**
[сгенерированный код]

**Анализ:**
- ✅ Верно: оба конструктора, наследование от Exception, поле bookId.
- ❌ Ошибка: отсутствует аннотация @Serial с serialVersionUID.
- ⚠️ Улучшение: можно добавить статический фабричный метод forBook(long id).

**Внесённые изменения:**
Добавлена аннотация @Serial, добавлен фабричный метод.
```

## 5. Защита работы

На защите лабораторной работы преподаватель вправе:

1. Попросить обучающегося пояснить **любую строку кода**, включая сгенерированную ИИ.
2. Задать вопрос о **принципах работы** применённых конструкций.
3. Попросить **модифицировать код** (например, добавить новое поле, изменить логику).
4. Проверить **журнал применения ИИ** и задать вопросы по анализу результатов.

Если обучающийся не может пояснить сгенерированный ИИ код или не ведёт журнал применения ИИ, работа может быть оценена ниже максимального балла независимо от её корректности.

## 6. Академическая честность

- Представление кода, полностью сгенерированного ИИ без понимания и модификации, квалифицируется как **академическая нечестность**.
- Использование запрещённых ИИ-инструментов (через VPN) приравнивается к нарушению академической честности.
- Обучающийся несёт персональную ответственность за корректность и безопасность итогового кода, независимо от способа его получения.

# Требования к оформлению отчётов

## 1. Структура отчёта

Отчёт по каждой лабораторной работе должен содержать следующие разделы:

1. **Титульный лист** (по установленному образцу).
2. **Цель и задачи работы**.
3. **Краткое теоретическое введение** (2–3 абзаца собственными словами).
4. **Листинги программного кода** с пояснительными комментариями.
5. **Протокол работы программы** — скриншоты или текстовый вывод консоли.
6. **Результаты выполнения индивидуального задания**.
7. **Журнал применения ИИ** (выписка из `docs/prompts/`).
8. **Ответы на контрольные вопросы**.
9. **Выводы** по проделанной работе.

## 2. Оформление кода

- Код приводится в отчёте с использованием моноширинного шрифта (Courier New, Consolas).
- Размер шрифта — не менее 10 пт.
- Длинные листинги (> 1 страницы) допускается выносить в приложение.
- Ключевые участки кода должны быть пояснены в тексте отчёта.

## 3. Сроки сдачи

- Отчёт по лабораторной работе сдаётся **не позднее начала следующего лабораторного занятия**.
- При наличии уважительной причины преподаватель может продлить срок сдачи.
- Незащищённые работы накапливаются; при превышении задолженности более 3 работ обучающийся может быть не допущен к итоговому контролю.

# Критерии оценивания

## 1. Балльно-рейтинговая система

Каждая лабораторная работа оценивается по 10-балльной шкале:

| Баллы | Оценка | Критерии |
|:-----:|:------:|----------|
| 9–10 | Отлично | Все задания выполнены полностью и корректно; код соответствует стандартам; применены ИИ-инструменты с критическим анализом; обучающийся свободно отвечает на вопросы |
| 7–8 | Хорошо | Задания выполнены с незначительными замечаниями; код работает корректно; применены ИИ-инструменты; обучающийся понимает код |
| 5–6 | Удовлетворительно | Задания выполнены частично; в коде присутствуют замечания; обучающийся понимает основную логику, но испытывает затруднения с деталями |
| 3–4 | Неудовлетворительно | Задания выполнены не в полном объёме; код содержит существенные ошибки; обучающийся не понимает собственный код |
| 0–2 | Неудовлетворительно | Работа не выполнена или выполнена формально без понимания |

## 2. Распределение баллов

| Компонент | Максимум баллов |
|-----------|:---------------:|
| Выполнение задания на паре | 4 |
| Выполнение индивидуального задания | 3 |
| Качество кода и соответствие стандартам | 1 |
| Применение ИИ с документированием | 1 |
| Ответы на контрольные вопросы | 1 |
| **Итого** | **10** |

## 3. Итоговый мини-проект (лаб. 16–17)

Итоговый мини-проект оценивается по 20-балльной шкале с учётом:

- корректности реализации ETL-пайплайна (5 баллов);
- стабильности при конкурентной обработке (3 балла);
- качества кода и архитектуры (4 балла);
- полноты документации и журналов промптов (3 балла);
- качества защиты и демонстрации (3 баллов);
- ответов на вопросы преподавателя (2 балла).
