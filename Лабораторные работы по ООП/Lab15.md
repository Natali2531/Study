## 2. Теоретический конспект

### 2.1. Что такое промпт

**Промпт (Prompt)** — запрос или инструкция, которую пользователь отправляет ИИ-ассистенту для получения желаемого результата.

### 2.2. Модель взаимодействия

```
┌─────────────────────────────────────────────────────────────────┐
│                    Модель взаимодействия                       │
│                                                                 │
│   Разработчик ──▶ ИИ-ассистент ──▶ Разработчик                 │
│   (промпт)          (генерация)       (анализ,                 │
│                                         проверка)              │
│         ▲                                      │               │
│         └──────────────────────────────────────┘               │
│                Итеративное уточнение                            │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3. Структура эффективного промпта

| Компонент | Описание | Пример |
|-----------|----------|--------|
| **Роль/Контекст** | Кто ты (специализация) | "Ты — senior Java-разработчик с 10-летним опытом" |
| **Задача** | Что нужно сделать | "Создай класс Order со следующими полями..." |
| **Формат вывода** | Как должен выглядеть ответ | "Предоставь полный код класса с аннотациями Jackson" |
| **Ограничения** | Что нельзя делать или что обязательно | "Используй Java 17+, добавь валидацию" |
| **Примеры** | Примеры входных/выходных данных | "Например: поле status должно быть enum" |

### 2.4. Принципы хорошего промпта

**1. Конкретность**
- ❌ Плохо: "Напиши класс для работы с заказами"
- ✅ Хорошо: "Создай Java-класс Order с полями id (long), customerName (String), items (List<OrderItem>), totalAmount (BigDecimal), status (OrderStatus), createdAt (LocalDateTime)"

**2. Атомарность**
- ❌ Плохо: "Создай REST-клиент, модель и тесты" (слишком много в одном промпте)
- ✅ Хорошо: Разбить на 3 промпта: модель → клиент → тесты

**3. Итеративность**
- Начинать с простого запроса, уточнять и расширять по мере необходимости
- Использовать цепочки промптов для сложных задач

**4. Антипаттерны**
- Размытые запросы ("Сделай что-нибудь")
- Отсутствие контекста ("Напиши код")
- Противоречивые требования
- Слишком длинные/сложные запросы

### 2.5. Цепочки промптов (Prompt Chaining)

**Цепочка промптов** — разбиение сложной задачи на последовательность простых запросов, где выход предыдущего промпта является входом для следующего.

```
┌─────────────────────────────────────────────────────────────────┐
│                      Цепочка промптов                          │
│                                                                 │
│  ┌─────────────────┐    ┌─────────────────┐                    │
│  │   Промпт 1      │    │   Промпт 2      │                    │
│  │  Проектирование │───▶│  Генерация      │                    │
│  │  архитектуры    │    │  кода модели    │                    │
│  └─────────────────┘    └─────────────────┘                    │
│         │                        │                             │
│         ▼                        ▼                             │
│  ┌─────────────────┐    ┌─────────────────┐                    │
│  │   Промпт 3      │    │   Промпт 4      │                    │
│  │  Генерация      │───▶│  Тестирование   │                    │
│  │  кода клиента   │    │  и анализ       │                    │
│  └─────────────────┘    └─────────────────┘                    │
└─────────────────────────────────────────────────────────────────┘
```

### 2.6. Чек-лист Code Review для сгенерированного кода

| # | Проверка | Описание |
|---|----------|----------|
| 1 | **Компилируется** | Код должен компилироваться без ошибок |
| 2 | **Обработка ошибок** | Есть ли try-catch, обработка исключений |
| 3 | **Логирование** | Есть ли логирование (SLF4J, Logback) |
| 4 | **Соглашения об именовании** | CamelCase для методов, PascalCase для классов |
| 5 | **Уязвимости** | Нет ли SQL-инъекций, XSS и т.д. |
| 6 | **JavaDoc** | Есть ли документация для публичных методов |
| 7 | **Тесты** | Есть ли юнит-тесты |
| 8 | **Принципы SOLID** | Соблюдены ли принципы SOLID |
| 9 | **Читаемость** | Понятен ли код, есть ли комментарии |
| 10 | **Производительность** | Нет ли проблем с производительностью |

### 2.7. Ограничения ИИ

| Ограничение | Описание |
|-------------|----------|
| **Галлюцинации** | ИИ может генерировать несуществующие API или методы |
| **Устаревшие знания** | ИИ может не знать последние версии библиотек |
| **Небезопасный код** | ИИ может генерировать код с уязвимостями |
| **Отсутствие контекста** | ИИ не знает специфику вашего проекта |
| **Предвзятость** | ИИ может быть предвзят в пользу определённых решений |

### 2.8. Принцип «всегда проверять сгенерированное»

```
┌─────────────────────────────────────────────────────────────────┐
│              Принцип "Доверяй, но проверяй"                    │
│                                                                 │
│   ┌──────────────────────────────────────────────────────────┐  │
│   │  1. Сгенерировал код                                     │  │
│   │  2. Визуальный осмотр                                    │  │
│   │  3. Компиляция                                           │  │
│   │  4. Запуск тестов                                        │  │
│   │  5. Code Review                                          │  │
│   │  6. Исправление                                          │  │
│   │  7. Повторная проверка                                   │  │
│   └──────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

## 3. Задание на паре

### Задача. Составление промптов и анализ сгенерированного кода

**Внимание! Лабораторная работа выполняется БЕЗ написания кода — только промпты и анализ!**

### 3.1. Часть 1. Составление промпта для генерации класса

**Задание:** Составить промпт для генерации класса `Order` со следующими требованиями:

1. **Поля класса Order:**
   - `id` (Long)
   - `customerName` (String)
   - `items` (List<OrderItem>)
   - `totalAmount` (BigDecimal)
   - `status` (OrderStatus — enum)
   - `createdAt` (LocalDateTime)

2. **Требования к промпту:**
   - Указать роль (ты — senior Java-разработчик)
   - Указать формат вывода (полный код класса с аннотациями для Jackson)
   - Указать ограничения (использовать record, если Java 17+, либо обычный класс)
   - Добавить требования по валидации

3. **Промпт должен быть структурирован:**
   - Роль/Контекст
   - Задача
   - Формат вывода
   - Ограничения
   - Пример (опционально)

### 3.2. Часть 2. Цепочка промптов для REST-клиента

**Задание:** Составить цепочку из 3 промптов для задачи «спроектировать REST-клиент для внешнего API».

**Задача:** REST-клиент для получения курса валют от внешнего API.

**Промпт 1:** Описать архитектуру классов (клиент, модель ответа, обработчик ошибок)
- Роль/Контекст
- Требования к архитектуре
- Формат вывода

**Промпт 2:** На основе архитектуры сгенерировать код модели ответа
- Использовать архитектуру из Промпта 1
- Сгенерировать POJO классы

**Промпт 3:** На основе архитектуры и модели сгенерировать код клиента с использованием HttpClient
- Использовать архитектуру из Промпта 1
- Использовать модель из Промпта 2
- Использовать Java 11+ HttpClient

### 3.3. Часть 3. Code Review сгенерированного кода

**Задание:** Для каждого сгенерированного ИИ фрагмента кода провести code review по чек-листу:

1. Компилируется ли код?
2. Обработаны ли ошибки?
3. Есть ли логирование?
4. Соблюдены ли соглашения об именовании?
5. Нет ли уязвимостей?
6. Есть ли JavaDoc?
7. Соблюдены ли принципы SOLID?
8. Понятен ли код?
9. Нет ли проблем с производительностью?
10. Можно ли улучшить код?

### 3.4. Часть 4. Сравнение ИИ-инструментов

**Задание:** Использовать минимум 2 разных ИИ-инструмента для одного и того же промпта и сравнить результаты.

**Сравнение по критериям:**
1. Качество кода (структура, читаемость)
2. Полнота решения
3. Соответствие требованиям
4. Наличие документации/комментариев
5. Обработка ошибок
6. Общее впечатление

### 3.5. Часть 5. Документирование

**Задание:** Документировать все промпты и результаты анализа в README репозитория.

**Структура README:**
1. Введение (цель работы)
2. Промпт для генерации класса Order
3. Цепочка промптов для REST-клиента
4. Результаты code review
5. Сравнение ИИ-инструментов
6. Выводы
